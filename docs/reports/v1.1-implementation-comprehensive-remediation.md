# BoxPorter V1.1 架构对照与彻底整改方案

> 最终版本：`2026-08-14`
> 范围：`/Users/alamn/BoxPorter`
> 审计目标：按《搬运猴_BoxPorter_24x7无人值守AI工作台完整规划书_V1.1.md》与现有代码的真实偏差进行“可执行”修复，而非报告级修辞修补。

## 0. 结论先行（Executive Summary）

- 系统已具备**任务/Run/Attempt 核心状态闭环**，但整体仍处于“后端内核可运行、前端入口不可用”的局部可达状态。
- 目前最关键阻塞是：**Web 侧没有从“需求输入”到“任务创建成功”完整起始链路**。
- 在“执行能力”与“可用性体验”上，当前不是“功能缺失”，而是**入口与产品语义未对齐**。
- 需要按“彻底改动”执行一轮“重构式补齐”：
  1) 重建任务启动入口体系；
  2) 落实恢复能力边界与提示；
  3) 把文档、报告、前端、API 的状态口径统一为同一真相源。

---

## 1. 关键事实核对：架构 vs 代码

### 1.1 已到位（可复用）

- 状态机（Task/Run/Attempt）严格定义并贯穿核心调度：`src/boxporter/core/state.py`
- 调度+观察闭环（终态推进、提交/审核/失败处理、Run handle 清理）：`src/boxporter/core/scheduler.py`
- WatchDog/Recovery 的故障分类与策略：`src/boxporter/core/watchdog.py`, `src/boxporter/core/recovery.py`
- 重启恢复与无 pid 并发态处理（避免伪造 Handle）：`src/boxporter/core/reconcile.py`
- Runner 注册工厂与能力声明：`src/boxporter/runners/__init__.py`, `src/boxporter/runners/openhands.py`
- Web API 基础读写与事件流框架：`src/boxporter/api/app.py`
- 命令层调度触发入口：`src/boxporter/cli_v2.py`

### 1.2 明确缺口（当前用户痛点）

- 前端缺少“新建任务”启动入口；用户无法从页面完成从文件/表单到创建动作。
  - `src/boxporter/web/index.html`
  - `src/boxporter/web/app.js`
- API 接口仅是 `POST /api/tasks` JSON 提交流程，未提供“文件选择/上传/拖拽”配套。
  - `src/boxporter/api/app.py`
- 报告体系与当前实际行为存在口径漂移（“已完成/部分满足”与可见行为不一致）。
  - `docs/reports/v1.1-implementation-report.md`
- 开关与边界未透明化：OpenHands 已声明不支持 checkpoint/resume，但前端与任务说明未把恢复边界显性化。
  - `src/boxporter/runners/openhands.py`

### 1.3 根因判断

- 不是后端“算法未写”导致失败；是**功能入口与产品契约错位**。
- 架构文档设计为“可操作工作台 + 四箱/任务创建闭环”，当前实现更接近“服务端运行核心 + 任务列表控制台”。
- 这是典型的“可达性缺陷”，优先级高于再优化单点逻辑。

## 2. 设计偏差清单（按严重度）

### P0（阻塞使用，必须优先）

1. `tasks` 创建入口缺失（Web）
- 现状：只可查看已有任务，无法就地创建。
- 风险：系统看起来“不能开始任务”，实际能力与交互严重不匹配。
- 影响范围：所有用户操作起点。

2. 文件导入与粘贴输入缺失（Web + API）
- 现状：未提供从本地文件快速构建任务Spec的通道。
- 风险：用户无法批量启动或重复提交规范化任务，产线自动化失效。

3. 创建成功反馈与 READY 状态可视化不足
- 现状：即使后端成功创建，前端未形成清晰路径提示。
- 风险：用户误判失败，执行链路中断。

### P1（高优先，不阻塞但会产生系统误用）

4. Runner 恢复能力边界不透明
- OpenHands 明确不支持 checkpoint/resume；当前状态下需要在 UI 与任务说明中显式提示。

5. 报告口径与实际实现不一致
- 当前报告内容存在“修复完成”与“体验未达标”混叠。

### P2（完善体验与可维护性）

6. 文档中的用户流程与前端页面缺少同步
- 架构草图中的“启动/操作流程”没有完整映射到 UI。

7. 任务创建成功后的默认策略与可观测性尚需增强
- 需要统一 creation -> ready -> running 的提示、失败原因映射与阻塞原因展示。

## 3. 彻底整改方案（从架构层面重建，不是打补丁）

### 3.1 构建“任务启动总线”

目标：让“选择文件/写 spec -> 校验 -> 创建 -> READY -> 可运行”形成同一流程。

#### 3.1.1 后端 API 重构

- 在 `src/boxporter/api/app.py` 增加 `POST /api/tasks/import`（可选）：
  - 支持 `multipart/form-data`（文件+可选文本 fallback）
  - 自动解析 JSON、校验 schema（title/objective/acceptance_criteria/workspace）
  - 解析失败返回结构化错误（字段+位置+修复建议）
- 保留现有 `POST /api/tasks`，作为精简 JSON 主路径。
- 统一错误响应模型：`code`, `field`, `message`, `hint`, `trace_id`。

#### 3.1.2 前端任务创建面板重建

- 在 `src/boxporter/web/index.html` 新增 `New Task` 区块（弹窗/侧边侧栏二选一）。
- 在 `src/boxporter/web/app.js` 实现：
  - 本地 `.json` 文件选择（`input[type=file]`）
  - 复制粘贴 JSON 直接创建
  - 基础 schema 校验（必填项 + 类型 + 长度）
  - “创建任务”按钮的加载态、失败态、成功态与自动跳转
- 标准提示文案：
  - 创建成功后显示任务 ID + 当前状态（PENDING）
  - 自动显示下一步按钮：`Mark Ready`

#### 3.1.3 任务启动与观测体验

- 在任务列表增加“最近创建任务”高亮区，显示 `created_at / state / runner / error hint`。
- 创建成功后自动刷新任务列表并跳转详情页。
- 详情页增加 “启动条件检查”模块（workspace 可写、依赖文件存在、spec 合法）。

### 3.2 把恢复能力边界变成用户可理解的产品能力

- 在 `src/boxporter/runners/openhands.py` 的能力定义上层增加“恢复策略摘要”文案。
- 在前端 Runner 展示页/任务页增加能力矩阵：
  - checkpoint: true/false
  - resume: true/false
  - restart_on_failure: 支持/不支持
  - fallback: 说明（不支持时将走新 Attempt）
- 这样可以避免用户误以为“停机后会继续同一会话”。

### 3.3 统一报告为单一真相源（Docs Contract）

- 用一份报告替代“多报告竞合”：
  - `docs/reports/v1.1-implementation-report.md` 仅记录“当前事实”
  - `docs/reports/v1.1-implementation-comprehensive-remediation.md`（本文件）仅做路线与整改决议
- 增加“同步规则”：
  - 每次功能变更必须同步更新：
    1) 任务清单（状态）
    2) P0/P1 列表
    3) 部署现状
    4) 验收清单
  - 未更新即视为“文档状态不可信”。

### 3.4 运营可靠性（实机）对齐

- 远端入口与本机入口统一，明确边界：
  - 本地开发：127.0.0.1
  - 生产远端：网关/Tailscale/反向代理（后置）
- 继续保留已有长稳测试、重启恢复、watchdog 验证。

## 5. 严格验收标准（可执行）

### 功能验收

- 从 Web 页面可选择本地 `.json` 并创建任务。
- 任务创建返回成功后状态从 `PENDING` 变为 `READY`（或可见阻塞原因）。
- 所有创建失败必须返回可读字段化错误，不允许仅返回纯文本。

### 可靠性验收

- 入口失败重试不导致重复任务（依赖 idempotency 语义）。
- OpenHands 恢复边界在 UI 与任务详情中可见并一致。
- Watchdog+reconcile 观察到崩溃后任务可进入预算内恢复路径。

### 文档验收

- 报告中的每一条“已完成”在代码中可被定位到文件/测试。
- 无“部分完成”同时在体验中无法验证到位。

### 运维验收

- 所有新 API 接口需有错误模型、trace-id 和用户可见提示。
- 关键动作必须有审计事件（创建/准备/审批/重试/归档）。

## 6. 风险与回退策略

1. 风险：一次性重构前端会影响既有页面状态。
   - 回退：先保留原任务列表视图，仅新增独立创建模块；创建成功路径验证通过后再合并状态展示。
2. 风险：文件导入带来不可信 spec。
   - 回退：保持服务端 schema 严格验证与错误拒绝，日志保留首个错误。
3. 风险：文档同步滞后。
   - 回退：设置“文档检查清单”为 PR 检查项。
