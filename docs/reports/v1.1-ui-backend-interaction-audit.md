# BoxPorter V1.1 后台 UI + 后端交互审计修改文档（严格按规划稿）

> 审计时间：2026-08-14（基于 `/Users/alamn/BoxPorter`）
> 参照：`搬运猴_BoxPorter_24x7无人值守AI工作台完整规划书_V1.1.md`

## 结论摘要

- 核心闭环（任务状态机、调度、watchdog、reconcile）已具备；你在本窗口看到的主要问题不再是“完全不能开始”，而是“启动链路与规划稿功能面不完整/前后端不一致”。
- 依据规划稿，后台 UI 仍缺失“项目化入口 + 运行页 + 完整 API 约定 + 交互可追溯反馈”。
- 当前已经有“新建任务弹窗 + 文件文本输入 + 就绪检查 + ready 按钮”。但这是**修复后的补齐版**，并未覆盖规划里的所有交互语义。

## 关键偏差（按严重度）

### P0（阻塞真实生产使用）

1. **Run 管理 API 与规划稿不一致**
- 规划稿 API 草案要求：`GET /api/runs/{id}`、`GET /api/runs/{id}/events`、`POST /api/runs/{id}/resume`（规划 15.3，行 1773-1776）。
- 当前实现只有 `POST /api/runs/{run_id}/stop`，缺 `get`/`events`/`resume`（`src/boxporter/api/app.py:617`）。
- 风险：无法在后端做 Run 级检视、恢复与运维操作；与“实时页/运行页”草图冲突。

2. **后台系统健康只展示单点状态**
- 规划要求“系统健康拆分显示 Control Plane、数据库、OpenHands、Runner、磁盘、备份、远程入口”（规划 16.2、1860）。
- 当前 `/api/system/health` 仅返回 `database` 状态 + `ok` 字段（`src/boxporter/api/app.py:206`），UI 仅显示一个绿色/黄色徽标（`src/boxporter/web/app.js:466`）。
- 风险：局部故障掩盖，运维误判。

3. **任务列表交互未覆盖规划的项目域模型**
- 规划要求“项目/Operations/Settings 分层导航，四箱看板具备项目上下文与筛选”（规划 16.1、16.3）。
- 当前导航仅 `总览/任务/事件/审批/系统/设置/会话`（`src/boxporter/web/index.html:16-23`）；`loadDashboard` 默认取首个 project（`src/boxporter/web/app.js:75`），无项目选择/过滤。
- 风险：多项目场景下无法按项目运营。

### P1（严重体验和可维护性影响）

4. **`/api/tasks/import` 在交互上未被前端消费**
- 后端有导入 API（`src/boxporter/api/app.py:297`），但前端任务创建按钮始终走 `/api/tasks`，文件读取后在前端 parse 再提交（`src/boxporter/web/app.js:356-365, 387`）。
- 结果：导入契约冗余、错误返回语义分裂、无法利用后端统一的文件解码与结构化报错。

5. **事件流断线补齐没有落在任务执行交互**
- 规划实时页要求“事件游标和重连补齐”（16.5、1932）。
- 后端 `SSE` 读取 `Last-Event-ID` 与 `after_cursor`，有机制（`src/boxporter/api/app.py:945`）；前端不持久游标，不回放历史，也无重连态提示（仅 `conn-badge`）。
- 风险：离线期间缺失关键状态变化，任务动作后无可追溯链路。

6. **任务创建成功后的后续动作不一致**
- 前端在详情页和弹窗里都给“标记 READY”，但缺少 “创建时明确指定 `project_id` 下拉选择、重复提交防护（Idempotency-Key）” 的交互约束。
- 规划强调“所有写 API 支持幂等、任务可从 PENDING 可视化进入 READY”（15.3、1711；6.3）。
- 当前未传 `Idempotency-Key`，重复点击可能重复创建，且 `submitTaskCreation` 无项目上下文验证（`src/boxporter/web/app.js:387`）。

### P2（后续质量缺口）

7. **任务详情/实时页信息不足**
- 规划 16.4/16.5 需要标签页（事件、Terminal、提交包、审核、成本）与 Run 终端视图；当前详情页只展示摘要+run 列表+事件尾帧（`src/boxporter/web/app.js:166` 之后）。
- 风险：无法快速闭环审核证据与运行健康。

8. **审批与阻塞动作没有统一的流程页**
- 规划 16.7 建议阻塞/审批共用列表与责任人动作；当前审批页只列表待处理项目，没有 blocker 列表页面（`src/boxporter/api/app.py:710` 有 approvals 列表/操作，但 UI 未展示 blocker 专页）。

## 根因判断

- 根因不是核心执行引擎缺失，而是“UI 语义层与规划草图的产品能力定义不一致”。
- 部分后端接口已实现，部分未实现，但前端依赖仍按旧约束编写，导致用户感受“界面有入口但能力不完整”。
- 风险主要是：用户能看到任务卡片，但看不到可执行运行页和恢复动作路径。

---

## 修改方案（严格执行版）

### 目标
- 将后台控制面从“任务增删列表”提升为“项目级 -> 箱体 -> 任务 -> 运行页 -> 运行控制 -> 事件审计”的闭环。
- 任何关键动作必须可在 UI 上触发并有明确后端可验证 API 映射。

### 阶段 A：必须先做（P0/P1 收敛）

1. 完成 Run API 与 UI 绑定
- 后端新增/补齐
  - `GET /api/runs/{id}`：返回 run 基础信息 + task/attempt + lease + 运行指标（若可得）。
  - `GET /api/runs/{id}/events`：事件分页与 cursor。
  - `POST /api/runs/{id}/resume`：受策略与审批控制，调用调度/恢复动作。
  - 对应参考：`src/boxporter/api/app.py` 中 `stop_run` 位置（617 起）延展。
- 前端新增“实时运行页”入口与列表
  - 任务详情页增加 `RUN` 链接到独立 run 视图。
  - 视图中支持 `暂停/停止/续跑（resume）` 按钮（受状态机约束）。
  - 实时页展示 `seq`、`event_type`、`occurred_at`、`payload`，并显示连接状态。

2. 落实导入接口的一致性
- `/api/tasks/import` 作为“单入口”用于文件与文本导入。
- 前端文件模式直接 `multipart/form-data` 调 `POST /api/tasks/import`，不用前端自己 `JSON.parse` 再走 `/api/tasks`。
- 文件导入和粘贴模式共享“字段规范 + 错误码映射 + trace_id 回显”。

3. 统一系统健康视图为多组件面板
- 后端 `/api/system/health` 新增字段：`control_plane`,`openhands`,`runner_registry`,`disk`,`backup`,`remote_access`。
- UI 显示明细 badge 和警戒状态，不再用单点绿灯。

4. SSE 游标 + 重连策略对齐
- 后端在 SSE 流事件中保证 `Last-Event-ID` 与 `after_cursor` 一致。
- 前端维护 `lastEventSeq`，重连前回传并补齐；断线后显示 “重连中” 状态。

5. 幂等与重复提交保护
- 前端每次创建任务、ready、stop、review、approve 等关键写请求加 `Idempotency-Key`（可基于 `clientSessionId + ts + action`）。
- 提示“重复提交请使用同一任务 ID 回退”

### 阶段 B：高价值体验（P1/P2）

6. 项目域和四箱交互重构
- UI 新增项目选择器；`loadDashboard/loadTasks` 按 `project_id` 获取。
- 任务卡补充字段（预算、risk、依赖、租约、最近进展）。
- 四箱卡片支持“检查条件弹层”，点击不直接迁移状态（仅发迁移提案）。

7. 任务详情页结构化扩展
- 采用 16.4 模式标签页：
  - 概览（目标/验收/依赖）
  - 运行（run 列表 + run 快捷入口）
  - 事件（分页）
  - 提交包（artifact hash）
  - 审核（review 历史）
- 对应 `openTask` 重写成分区渲染。

8. 阻塞与审批闭环
- API 层补 `GET /api/blockers`（或从 task 查询聚合 blocker 列表）；UI 添加阻塞看板。
- 审批列表增加 `required_inputs/approver_scope/expire_at` 列，操作分流到高风险确认。

## 验收标准（定量）

1. 能否从后台完成一次 `project -> new task(json/file) -> ready -> running -> run page -> stop/resume -> final` 全链路。
2. `/api/tasks/{id}` 返回 `task` 与 `runs` 后，用户可从 UI 一步到位进入 `run` 详情。
3. SSE 断线 10 秒内恢复后，事件序列无跳号（按 `seq` 断点补齐）。
4. `/api/system/health` 在 runner/数据库/备份/远程入口中至少 1 项异常时，健康 badge 显示警戒并显示触发项。
5. 文件导入时，非法 JSON/字段缺失/非法 task_id 返回结构化错误（`code/field/hint/trace_id`）。

## 风险与回退

- 风险 A：新增 Run API 后前端逻辑大改，影响旧用户习惯。
  - 回退：保留原任务列表/详情页作为 fallback。
- 风险 B：恢复动作（resume）与调度策略冲突。
  - 回退：在 `resume` 入口加入状态检查与 confirm，返回明确拒绝原因。
- 风险 C：健康组件化指标与实际探针不一致。
  - 回退：采用只读字段，采集失败则 `unknown`，不影响主流程。
