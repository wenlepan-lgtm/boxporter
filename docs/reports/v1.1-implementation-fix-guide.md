# BoxPorter V1.1 实施报告修复指引（按可执行清单）

## 结论

当前 `v1.1-implementation-report.md` 中标注“关键闭环已交付”存在偏差。
在现有代码里至少有 4 个高优先级缺口：

1. 调度启动通路未注入任何 Runner（daemon/tick 在“空注册表”上运行）。
2. Tick 没有基于 `runner.observe()` 推进运行生命周期（运行结束后不能自动进入 REVIEW 或 FAIL 流程）。
3. OpenHands 无 checkpoint/resume，`reconcile` 仅占位且不会复活真实会话。
4. Approval 的 `consume()` 有接口和存储能力，但未接入任何执行决策路径。

这意味着该报告里“139 项测试通过”并不等于生产闭环的可运行状态。建议先按 P0/P1 分层修复，随后再更新报告状态。

## 目标状态（修复后应该满足）

1. Daemon 在首次启动时可稳定注册至少 1 个可用 Runner。
2. Run 完成/失败观测被纳入 tick 主循环并推动状态变更。
3. Run 恢复/检查点链路明确：要么支持恢复与重挂，要么明确报告“不能恢复”。
4. 高风险动作在执行前必须消费 approval，否则不得执行。

## P0 修复：必须先做

### A. 给调度器注入 Runner（不再使用空注册表）

**现状证据**
- `src/boxporter/cli_v2.py:151-153`、`src/boxporter/cli_v2.py:173-176` 在 tick 命令新建 `RunnerRegistry()` 后未注册。
- `src/boxporter/cli_v2.py:336` 直接把空 registry 传给 daemon。

**预期改动**

1. 新建 Runner 工厂入口（建议 `src/boxporter/runners/__init__.py`）：
   - 默认注册 `OpenHandsAdapter`（带 env/API-key 保护）。
   - 可选注册 `DeepSeekHarnessRunner`。
2. `src/boxporter/daemon.py:58-60` 的 `startup` 前后确保实例化 daemon 时，registry 已包含 runner。
3. `src/boxporter/cli_v2.py` 的 `tick`、`tick-policy`、`daemon` 三类入口都改成复用同一 factory，不再重复构造“空对象”。

**验收**

- `task-1` READY 后执行 daemon tick，`runs` 表出现行且 `runs.state=STARTING/RUNNING`。
- `event` 出现 `RUN_CREATED`、`TASK_WORKING`。


### B. Tick 主循环恢复 run 生命周期观测闭环

**现状证据**
- `src/boxporter/core/scheduler.py:122-176`：`tick()` 只做 recover/schedule + heartbeat，没做观察驱动的自动状态转换。
- `src/boxporter/core/scheduler.py:457-472`：`heartbeat_all()` 只对 `self.handles` 中已知运行进行 `inspect`，但没有后续状态变更逻辑。

**预期改动**

1. 在 `tick()` 中新增 `self._observe_active_runs_and_advance()`（建议在 heartbeat 之后）。
2. 对每个 active run 做 `runner.inspect(handle)` 并按 state 做闭环：
   - `RUNNING/CHECKPOINTING/WAITING_APPROVAL/STALLED`：仅记录进度与心跳。
   - `SUCCEEDED`（Executor）：
     - 若 `run.worktree` 下存在 `reports/result.md`,`reports/verify.md`,`reports/executor.md`，则触发 `SubmitExecutorRun`；
     - 否则落失败（`run` fail，带 `stop_reason`）或按策略进入 REVIEW_REQUIRED（建议先 fail）。
   - `CRASHED`/`TIMED_OUT`：转换为 `FailRun`。
3. 把运行级观察与任务级恢复动作并发执行，避免只靠 watchdog 触发。
4. 若 run 已终态，清理 `self.handles` 内该 handle。

**验收**

- Executor Runner 退出 `SUCCEEDED` 后，系统自动进入 `SubmitExecutorRun` 对应 `TASK_REVIEW_PENDING`。
- 运行直接 `CRASHED` 后，系统在一次 tick 内进入 `TASK_FAILED` 并进入恢复/重试策略。

### C. 重启恢复不能再次写出“伪 handle”，避免误判

**现状证据**
- `src/boxporter/core/reconcile.py:75-81` 对 active run 使用 `RunHandle(..., pid=lease.pid)` 占位。
- OpenHands 的 `start` 没有持久会话引用，`_runner_for` 依赖 `self._sessions`，重启后无法真实 inspect。

**预期改动**

1. 明确策略：
   - CommandRunner：根据持久 pid 可在进程活性范围内进行最小级别重附加。
   - OpenHands：缺少可重挂上下文时，`reconcile` 不假造 handle。
2. 当无法重挂时按安全策略直接 mark run 失败（或 blocked）而不是伪造“存活”；并写入清晰事件。

**验收**

- 主机重启后，`RUN_ACTIVE_STATES` 中的 OpenHands run 不再出现“无 context 但被当作可观察”的假阳性。
- `test_reconcile_after_db_reopen` 仍保证 state 一致。

## P1 修复：下一优先级

### D. OpenHands 检查点/恢复语义对齐（目前硬性不支持）

**现状证据**
- `src/boxporter/runners/openhands.py:214-247`：`supports_checkpoint=False`、`supports_resume=False`，`checkpoint()`/`resume()` 都抛异常。

**预期改动**

1. 明确 ADR 级行为：要么在报告里标注“OpenHands 无恢复语义”，并禁用涉及该 runner 的自动恢复编排。
2. 或者提供“降级替代”：恢复链路只在支持 resume 的 runner 上打开（例如 mock/command 方案）。
3. 如果未来加入可恢复能力：
   - `checkpoint` 存储到持久化位置并写入 `runs.checkpoint_ref`。
   - `reconcile` 对失败前活跃 run 按 checkpoint/ref 尝试重启。

**验收**

- 不能再在报告中写“Checkpoint/Resume 已闭环”；如果确实不支持，要在 ADR 与运行时能力页一致。

### E. Approval 消费接入执行点（高风险动作用）

**现状证据**
- `src/boxporter/storage/metering.py:221-237` 有 `consume()`。
- `src/boxporter/application/commands.py` 与 `src/boxporter/api/app.py` 可以发起/决定 approval。
- `src/boxporter/core/scheduler.py` 和 task/run 命令路径未消费该能力。

**预期改动**

1. 先定义高风险动作切入点（建议在 runner prompt / runner action 前）：
   - `send`、`stop`、`StartExecutorRun` 前统一加 policy 判定。
2. 引入 `RunnerExecutionGuard`（调度器或执行器封装层）：
   - 通过 `run.task_id` + `run.role` 查询最近未使用 approval；
   - 成功消费后才允许执行。
3. 消费失败时返回明确 `REJECTED`，并记录 `APPROVAL_CONSUMED` 失败事件（含 action/target）。

**验收**

- 在高风险任务上，无 approval 时不会启动/推进 run。
- 已批准的 approval 在单次使用后 `used_count` +1；超过 `max_uses` 阻止二次。

## 风险与回退策略

1. 自动 submit 依赖 `run.worktree/reports/*`，运行器若未按约定落盘会导致早期 fail；建议先做可观察到的可配置路径。
2. 一旦自动转移到 REVIEW_PENDING，失败样本会增加；需保留 `retry` 与 `STOP_AND_NOTIFY` 的旧策略。
3. 若需要立即发版，第一阶段可先把 OpenHands 恢复能力留白，但必须让报告明确“当前不支持恢复”，避免假阳性承诺。
